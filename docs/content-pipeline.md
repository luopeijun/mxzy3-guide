# 开发备忘：内容管线与渲染细节

给要改这个仓库的人看的一页：数据是怎么从原始资料变成 `public/data/guide.json` 的、
页面又是怎么把这些块渲染出来的，以及测试与提交相关的东西。改解析脚本或改正文样式之前先读这一页。

## 内容来源

- 《明星志愿3攻略.docx》（本地原始文档，不入库）：经纪人事件簿 / 艺人事件簿 / 六大特殊通告 / 其他事件四类的主体正文。「路欧桑剧情整理」原本是「其他事件」的最后一条，现在单独提成一个类目（`extract_guide.py` 建树时把这一项从 `other_items` 里 `pop` 出来插到第三位），正文仍来自 `sources/luousang-*.txt` 那五份分支文件。**类目 id 与五个分支 id 一直是 `other-events/luousang*`，提升时没有改名**，老书签、CG 落点、追踪器的分支线都靠它。
- `sources/game-initial-questions.txt`：开局访谈 14 题的完整选项与友好度变化，**以这份 txt 为唯一来源**，原文（GBK）转 UTF-8 后原样使用，不做改写。首行 `★标题` 只是页面标题（与页面同名时不重复渲染）；首个问题之前的说明行合并成一条黄底提示条；`问题结束（补充说明）` 的括号文字作为该选项的脚注（`hint`），选项本身仍显示「问题结束」终止标记。
- `sources/initial-events.txt`：初始事件（新手事件 1–5 / 女艺人的疑惑 / 女艺人的请求），**以该 txt 为唯一来源**，docx 里的同名章节不再参与渲染，原文（GBK）转 UTF-8 后原样使用。解析规则：首行 `★新手事件：` 是页面标题，跳过；`#`、`*` 开头与**以冒号结尾的独行标题**（`初始女艺人的事件（指…）：`）都解析为 `section`；章节内不含标点的短行（`女艺人的疑惑`）解析为 `heading` 子标题；编号行（`1 （自动）`、`3－1 （跟随）`）解析为 `event` 并保留编号与触发方式标签，`提醒：` 行渲染为提示条，「旗下艺人为…」缩进为选项样式。txt 里已经没有 `#初始剧情` 这个标签，所以第一个 `event` 之前若还没有任何 `section`，脚本会自动补一个「初始剧情」小节，让开局 5 条事件不再裸挂在页面下。正文里混用的 `--` 与半角逗号会统一成 `——` 与 `，`。
- `sources/character-stats.txt`：18 位可签约艺人（含资料片新增）的初始属性，**以游戏内「初始属性(女)」「初始属性(男)」两张截图为准**。源文件保持截图的行列形状：一段以角色名开头，随后是属性行与紧跟其后的 `成长` 行；女、男两段合并成**一张表**（`table` 块）而不分性别——一人一行、一项一列，每个格子上面是初始值、下面一行小字是成长加成。姓名列在窄屏横向滑动时保持固定；每列最高的数值套浅粉胶囊，成长加成的最高值用金色，**并列第一不标**。
- 文档里确实没有收录的条目（物品总览、贺总相关事件等）保留在树中并标注「待补充」，重跑脚本不会丢位置。

## 甜蜜乐章（sweet 站）

甜蜜乐章是与原站平级的第二个站点（`sweet.html`），共用同一套组件与设计令牌，但**数据、目录顺序、进度键全部另起一套**——改这边的正文永远不会碰到原站的 `public/data/guide.json`。

- 源文本都在 `sources/sweet/`，原始资料是本地 GBK 繁体 TXT，导入时转成 UTF-8 简体（`zhconv` 转码，全角数字与连接号统一成 ASCII，全角字母归 ASCII），入了 `sources/` 之后这些就是唯一来源，**不再回读本地原文件**。转换统一走 `python scripts/convert_sweet_source.py 关于天晴.txt:tian-qing.txt`（也接受 `约会/城仲瑄.txt:cheng-zhongxuan-date.txt` 这种子目录），转码规则与原文错字补正都写在脚本的 `FIXES` 里。
- `python scripts/extract_sweet_guide.py` → `public/data/sweet/guide.json`：目录结构（类目 / 每节标题 / 顺序 / 可选副标题）写在脚本的 `CATEGORIES` 里，正文按节名读 `sources/sweet/<slug>.txt`；没有对应 txt 的节点保留 `status: "missing"`，页面给「这一页还没整理」的占位提示。新增一节 = 加一条 `CATEGORIES` 条目 + 放一份 txt + 在 `PARSERS` 里登记解析函数。
- 事件页解析规则（主线、公司改建共用 `parse_event_page`）：首行是正文页副标题（与页面标题重复时不再重复显示）；不带编号的行是章节；`数字.标题` 是带编号的章节（`4.改建` → 标题取「改建」）；`数字-数字．标题` 是事件（编号进 pill、标题进卡头，句尾的 `．．` 统一成 `…`）；细节行按前缀决定类型——`时间：` / `概要：` / `条件：` 是普通段落，`提示：` 与 `（…` 是金色备注，**缩进可有可无**（公司改建的源文本就是顶格写的）。主线文末不带编号但含冒号的行视为作者注解，连同续行收进「结局分歧」一节；公司改建没有这段，解析时不开启该规则，避免误吞正文。
- 角色页解析规则（8 位共用 `parse_character`）：靠 `可创作作品：` / `事件：` / 三个「…条件：」小节切换四区，区外的编号行（`1.公司自制作品10个以上`）不当事件；事件标题尾括号只有在内容是 `友好度上升` / `好感度上升` / `CG` 时才拆成标记（CG → 玫红卡 + 金色徽标，其余 → 灰色 tag），`出去走走吧～（2）` 这种序号留在标题里；`*` 开头的作品是特殊作品（金色菱形），自带 `1、` 序号的作品行不再叠圆点。角色头像按 `<slug>-logo.*` 放 `public/images/sweet/`，探测到才写进节点的 `avatar`，目录与角色卡在人名左侧渲染圆圈头像（约定与主站 `images/characters/` 一致）。
- 约会选项（`<slug>-date.txt`，8 位角色都有）：`parse_date` 出「页首四行邀约门槛 + 两组对话」，`_merge_date` 把门槛接在基础信息后面、对话追加到页尾；地点是小标题，每个提问一个 `qa` 块（编号 pill + 问题 + 多行「答」），外壳与事件卡同一套。小节名后面带不带冒号各页不一致，入库时统一去掉；`提示：…` 走金色便签。
- 支线页解析规则（6 页共用 `parse_side`）：`#章节` 与「`1.变身`」（下一行是 `1-1.` 才认章）是小节；`1-1.xxx` 与 `（1）xxx` 是步骤卡；`条件：` / `附注：` / `附：` 自成小节，`公司结局：` / `感情结局：` 是圆点条目；`※` 与 `提示：` 是卡内备注，续行留在同一步里。
- 表格页解析规则（国外通告）：首行是副标题，之后每三行一组「城市 / 公司（类型）/ 接拍条件」，校验总行数是 3 的倍数、公司行必须带全角括号，错位直接报错而不是生成半截表；产出一个 `kind: "table"` 块，前端复用通用的 `DataTable`。
- 目录按用户裁决：第一类叫「**经纪人事件簿**」（10 节，**不含「角色介绍」**），角色攻略 8 位（感情线与约会选项合并成同一个角色页），支线攻略 6 条（标题直接用角色名，不写「关于 X」），合计 24 节，**已全部有正文**。
- `scripts/test_sweet_guide.py`（26 项）：锁住「提交的 guide.json 与脚本重算完全一致」+ 各节章数与事件数（主线 4 章 23 事件、角色页 8 位、约会问答 8 页、支线 6 页）+ 事件都带时间与概要 + 表格内容 + 目录结构与「副标题只能来自原文首行」+ `cgIds` / `anchor` 与 `sources/sweet/cg-links.tsv` 完全对齐，防手改 JSON 导致的静默回退。
- **攻略 ⇄ CG 映射**：`sources/sweet/cg-links.tsv`（4 列：`cgId / nodeId / event|text / key`）由核对表 xlsx 经 `scripts/build_sweet_cg_links.py` 生成，`extract_sweet_guide.py` 的 `_apply_cg_links()` 把 `cgIds` 与 `anchor="ev<块下标>"` 写到命中的块上，事件类顺带补 `cg: True`（这样支线里没在标题标 CG 的步骤也渲染成 CG 卡）。`event` 按事件号精确匹配、`text` 按正文片段匹配；对不上直接报错，不会静默断链。
- 界面回归 `scripts/cdp_sweet_entry.mjs`：站点身份（标题 / `data-game="sweet"` / 粉色令牌）、目录 10-8-6、主线 23 张事件卡 + 5 条本页小节、公司改建 9 张、国外通告表格 5 行 3 列、角色页（事件卡 / 双标记 / 约会问答卡 / 白底与描边）、支线六页、CG 徽标点进图鉴、跨站胶囊，以及原站五个页签未受影响。
- **存档解析 `#/case`**：甜蜜乐章的 `.sav` 不能复用原版 `caseParser.ts`。文件头 4 字节是解压后长度，随后是 zlib 流；解压后主角名 @0x04、公司名 @0x19、签约艺人槽 @0x34/@0x38/@0x3c（−1 空）、游戏时间 @0x40。公司形象 / 知名度 / 公关在 `Firm` 段，标记 `[4]["Firm\0"]`，每条记录 `[编号][名字字节数][Big5 名字][NUL][知名度][公关][0]`，编号 1 是我方、数值 ×10 向下取整。艺人属性块头标记 `327680`，id 在 +16，九项能力从 +32 起；艺人姓名表从 `StarRole.dat` 烘焙进 `public/data/sweet/star-roles.json`。页面版式与主站存档解析一致（工具栏 / 游戏时间 / 公司 / 我方艺人 / 右侧本页小结）。真值快照在 `tests/fixtures/saves/sweet/Auto.sav`。

## 通告数据

通告库是**另一条独立管线**，和攻略正文互不影响：

- `sources/notices/notices.xls`：通告主表 + 角色表 + 三张参照表。11 个 sheet，其中 `电影/电视剧/广告` 表头在第 0 行、`唱片/主持` 因上方多一行「特殊要求」分组，表头在第 1 行、数据从第 2 行开始，脚本里按 sheet 分别写死起始行（`SHEETS[*].first`）。
- `sources/notices/requirements.xlsx`：只取其中的 `特殊要求影响` 表（搞笑 +2 亲和 / -2 叛逆 这类），其余 sheet 是「等级字母 × 星数 → 数值区间」的原始写法，和 `notices.xls` 里的 `说明` 表重复，因此不再解析。
- `python scripts/extract_notices.py` → `public/data/notices.json`（约 900KB，运行时 fetch，进入「通告」tab 才加载）。这条管线需要 `pip install openpyxl xlrd`，只有重生成数据时才要，跑站点不需要。
- 归一后的结构：`notices[]` 每条含 `cat / name / type / time / company / producer / brief`，外加 `roles[]`；唱片与主持没有角色表，用通告行本身合成唯一角色（`征求对象` 即角色名），电影/电视剧/广告的角色按 `通告编号` 回填。
- 复合特殊要求（`暴力反派`、`反串搞笑丑化`）在脚本里拆成 `specialKinds[]`，前端再按 `specialEffects` 查每天的三项增减。没给数值的（目前只有 `吻戏`）只显示要求本身，不加「无影响」之类的填充文案。
- **「能力影响」和「特殊要求影响」都是按天结算**：拍摄期间每天各结算一次，拍多少天就结算多少次，所以页面统一用「每天影响」表述，不做总量换算（表里没有天数）。角色表里的 `gains` 优先，缺失时回落到 `grades` 按类型给的数值。**数值口径**：`notices.xls` 的能力影响是十位数量级（36 / 48），游戏内每天实际结算的是它的 1/10（3.6 / 4.8），与 `requirements.xlsx` 的「能力影响（每天）」列逐格相符（203 格全是精确 ÷10）。所以 `extract_notices.py` 用 `daily()` 统一乘以 `GAIN_SCALE = 0.1` 再落盘，JSON 里存的就是游戏内数值；`叛逆 / 性感 / 亲和` 三列是接演门槛，不参与换算。改口径只需动这一个常量。
- `说明` 表除难度对照外还有几段散文（独家代理限制、S/L 刷属性、数据来源），脚本按「整行只有一个非空单元格且够长」筛成 `notes[]`，在「能力对照」页末尾照录；`取消隐藏即可重新显示` 那句是对着 Excel 说的，直接跳过。
- **能力要求不在数据里展开**：`grades`（类型 × 对象 → A/B/C/D）与 `scale`（星级 × 字母 → 区间）分开存，前端用 `requirementsFor()` 现算，换算法不用重生成 JSON。区间的正确性由 `scripts/test_notices.py` 兜底——它把 1100 多个「类型/对象/能力/星级」组合与原 xlsx 逐一比对，必须完全一致。
- **列表按页渲染**：默认每页 24 条（可选 12 / 24 / 48 / 96），分页器在 `NoticePager.tsx`，只挂当前页的卡片。分页器只留上一页/下一页两个箭头，首页与末页靠页码序列本身（`pageSlots` 始终把 1 和末页排在两端），远距离跳转用「跳至 N 页」。列表列数用 `repeat(auto-fill,minmax(min(340px,100%),1fr))` 跟着容器宽度走，不绑视口断点——1120 起右栏出现会把列表压窄，自动退回一列；900 这种「没有右栏但也不宽」的尺寸反倒排得下两列。卡片简介整段展开、不截断，同页卡片的最小高度由 `NoticesApp` 量完这页最高的一张再统一设上——量的是内层 `[data-notice-card-inner]`，量之前先把上一轮写上去的 `minHeight` 同步摘掉再还原，否则量到的是撑过之后的高度、翻到简介更短的页也缩不回去。同一个征求对象出现两次（特殊要求不同）就并排两个 chip，不折成 `×2`。
- **卡片的信息位固定**：右上角五颗星（`StarBadge`，点亮几颗就是几星，区间难度把「一定满足」的星打成实心金、可能区间打成半透明）、名称、类型/时间/公司三格元信息、角色行。剧种细分（连续剧 / 单元剧 / 短片）与广告篇名收成类型格标签行里的一枚小徽章，不再占第三行——否则这一格会比旁边两格高一行，三格对不齐。徽章用 `--color-series*`（中性石板蓝），原来的 tag-scene 青绿和「电视剧」分类 pill 撞色。
- **元信息配色（时间 + 公司）**：`infoStyle.ts` 把时间四档映射到 `text-year-1/2/3/x`（同族深色文字，L21–30，卡面上 ≥4.5:1），公司映射到 11 枚 `bg-dot-*` 索引点（统一 S42/L36–44 的一族 muted 色，色相按行业分组：电视冷蓝、音乐紫粉、电影红、广告金棕、经纪绿/灰紫）。分工原则是「大块颜色给有顺序性的时间、点缀给公司」——色相允许与既有令牌相邻，但 hex 一律不重复；时间色与最近旧令牌的 RGB 距离、点色两两距离都在落地前用脚本核过。没登记的公司/时间回落墨色与灰点。角色 chip 里有默认艺人的直接把艺人名写出来（粉底实线），没人接的只有角色与星数（灰底虚线），不再写「待定」字样，也不再有 `待定 N` 汇总行；星数在 chip 里写作 `4★`（五颗星留给卡片右上角与详情标题）。
- **能力对照是便签墙**：`ReferenceView.tsx` 把五块内容排成 `grid`，窄表（难度换算、特殊要求影响）并排占一行，宽表（类型能力要求、艺人成长率）`col-span-2`；每块顶部一条 3px 色带 + 标题同色圆点当作索引，不再是「一列铺到底、每块只占左半边」。右侧 176px 的「本页小结」是滚动定位器：点条目把对应便签滚到容器顶部（`scrollTo` + 减去 8px 留白），滚动时按「顶部已越过容器上沿且最贴近上沿的那块」反高亮——并排两块会同时越线，所以不能简单取最后一块。小于 1120 收藏起 rail，单列便签照常。
- **七种特殊要求各有一个色相**：`specialStyle.ts` 把搞笑（琥珀）、反串（墨绿）、暴力（砖红，`--color-alert*`）、反派（暗玫）、裸露（紫）、丑化（暖灰）、吻戏（品牌粉）分开，每个标签带同色圆点和描边；没登记的标签回落到中性灰，不会因为新增标签而消失。`cdp_notices.mjs` 断言七行样式的 class 两两不同，防止以后被合并成同一个灰 chip。

## 六大通告条件表

这是**第三条独立管线**，和通告库、攻略正文都不共用解析脚本。它现在只提供「六个目标有哪些条件」这份数据，供存档解析页的六大通告助手读取；刻意不自动从攻略正文抽条件（条件散在提醒句、括号、区间、否定和时间窗里，抽不准且改一句就崩）：

- `sources/special-notices.tsv`：人工维护的唯一内容来源，156 行 × 13 列（BOM + 换行），六个通告各一列拆成行。**条件行 89 条**、**只读备注行 67 条**（时间线、事件节点与「注」，零状态、不计数）。`verify` 列保留 10 条裁决的依据；只要还有 `?` 开头的疑点，运行时数据就拒绝生成。改这张表时按字节补，别手抄整份（弯引号会被改成直引号）。
- `scripts/build_specials_review.py`：校验表结构、把 `节点id#事件号` 逐条对到 `guide.json` 的事件块、生成 `outputs/specials-review.html` 审阅页（不入库）。10 条裁决记录在 `DECISIONS` 常量里，改表时可回查。
- `scripts/extract_specials.py` → `public/data/specials.json`（约 56KB，存档解析页挂载助手时 fetch）。生成时**复用审阅页那份节点与深链校验**。守护测试在 `scripts/test_extract_specials.py`（11 项），其中两条是硬拦：表里塞未裁决疑点、或事件号写成不存在的 `#9999`，都必须直接失败。

- **昆仑历险的角色位与事件链**：三坑数值门槛完全相同，继续共用 `slot=main` 的四行数值，艺人匹配只按性别贴「男主角 / 女主角」，不把分母拆成三份。8 条 `kunlun.node.*` 只读事件节点按用户时间链落表（还清欠款与塔罗小魔女 → 塞外观光后长城路老爹 → 累计 3 次观光 → 第三年 1 月后剧本 → 全球找王瑞恩闲聊 → 一周后再闲聊 → 一个月后再闲聊 → 集齐道具与证书后闲聊 → 全球预约），链接指向攻略事件 `#62/#63/#64/#66/#68/#69/#70/#71`。四件道具的 `hint` 写实际入手方法：益智休闲类主持第 8 次赠送 / 巴黎买女装买走当季款 / 日本旅游累计大于 9 次旅行社赠送 / 开罗有售；hover 道具胶囊直接透传这条 hint。证书在正文仍保持「一个证书一行，后面跟艺人」：`kunlun.cert.*` 的 `scope=artist` 让每行能按存档持有证书读到艺人，`caseSpecials.ts` 再用 `ROLE_CERT_NOTICES` 按 `slot` 重组为 `ArtistMatch.roleCerts`——男艺人只判男主角（戏剧 + 音乐），女艺人同时判女主角一（舞蹈 + 戏剧）与女主角二（舞蹈 + 音乐），各自独立算「证书齐备 / 证书未齐」并在艺人匹配 hover 里逐张证书列出；证书行留在 `phase=prepare`，不进四位数值的坑位分母。**绿勾不等于数值满格**：昆仑艺人胶囊要 `match.met === match.total` 且 `roleCerts` 全齐才变绿（Ending0004 姚子奇 4/4 但缺男主证书，必须保持灰）；银河团体胶囊要团体条件全满且 `group.certs` 全员持证才变绿（Ending0004 莎亞之音 7/7 + 舞蹈证书齐全应打绿勾）。胶囊上同时写 `data-case-special-complete` 方便浏览器回归核对。
- 状态文案：全部可判定条件达标写「存档条件已达成」，只差一项写「差 1 项」，其余按有无进展写「推进中 / 未开始」，分母为零写「待手工确认」。不显示假精确百分比，进度条只作视觉辅助。

## 存档解析（#/case）

独立的一页，只读明星志愿3 繁中三合一原版的 `.sa2`，甜蜜乐章不适用。文件用 `File.arrayBuffer()` 读进内存，不上传也不回写；游戏之后覆盖自动存档不影响已经解出来的那份快照。

- 静态表 `public/data/case-tables.json` 由 `scripts/build_case_tables.py` 从游戏安装目录的 `data/` 烘焙：`*Case.dat`（通告名 / 类型 / 公司）、`NeedEffect.tab`（类型 × 对象 → 等级）、`Difficulty.tab`（星级 → 数值区间）、`StarRole.dat`（艺人名字与性别）、`Nickname.tab`（艺人称号编号 → 名字 / 线 / 门槛）、`Firm.dat`（制作公司）、`Item.dat`（道具属性、说明、送礼好感向量）。解析在 `src/lib/caseParser.ts`，渲染在 `src/components/case/CaseReaderApp.tsx`。
- **送礼好感表真源在游戏里**：`Item.dat` 每条道具记录的尾字段里有 21 个定长槽位（`fixed[6:27]`，值 0–4），每个槽位对应一位可签艺人的送礼加成；不是独立 `.tab` 文件，也没有单独的「送礼数值表」。用 `sources/favorites.txt` 的 ＋4 / ＋3 真值反查确认槽位映射，烘焙成 `gifts: 道具编码 -> 21 槽位向量` 与 `giftSlots: 艺人编号 -> 槽位`（0 / 16 / 20 未使用，所以没有艺人映射过去）：1–12 → 1–12、65 → 13、74 → 14、75 → 15、72 → 17、76 → 18、77 → 19。当前 310 件道具 × 21 槽位、覆盖 18 位艺人；比攻略页更齐全（原缺 欧怡青 / 新名纱雪 / 卫亚 / 原少纬，也没有精确的 ＋1 / ＋2），因此已把这四位补进 `sources/favorites.txt` 并重生 `guide.json`，`favorite-items` 攻略页与存档解析页一致。唯一已知分歧是萧依莉的「蜂王精华露」：攻略写 ＋4、`Item.dat` 实际 ＋3，按「不依赖攻略网站」原则以游戏表为准。
- **两套数据目录，`data1` 优先**：三合一同时装了 `data`（2005-2006 初版）和 `data1`（2007 更新版）。自制通告那批 `CD6xx` / `CD7xx` / `TV7xx` 只有 `data1` 有名字（旧目录里缺 45 条，其中就包括 20 条自制通告里的 10 条），所以以 `data1` 为准、`data` 只补它留空的字段（CD274 的子类）。通告记录按**定长切片**取字段（名字 10、类型 50、子类 70、公司 116 或 108），不能按文本段序号取 —— 有一条记录子类留空就会整体错位，把出品公司读成剧情描述。`StarRole.dat` 反过来只有旧目录那份布局可用（`data1` 里那份读出来全是控制字符），`load_stars()` 挑能读出整张名单的那一份。
- **工作天数 / 每週上限的真源是 `sources/notices/notice-length.csv`**（39 行，玩家整理，含甜蜜乐章的舞台剧 / 时装秀三条，繁中三合一的 `Length.tab` 里没有这两类）。脚本按简→繁映射喂进 `length` 表，并把结果与游戏自带的 `Length.tab` 逐条对照：数值不一致、`Length.tab` 里多一行而 CSV 缺、CSV 出现没登记过的类型写法，三种情况都直接报错退出。**天数按角色类型查 `种类|角色`，不是整个通告一个值**：连续剧男主角 45 / 女配角 20、电影男主角 40 / 男配角 25，同一通告里各有各的天数。解析给每个 `RoleRecord` 写回自己的 `workDays / daysPerWeek`（`notice.workDays` 仍留第一个命中角色的值供 CSV 用）；筹备中表格按「一角色一行」在「执行期间」列逐行渲染各自的工作胶囊（起止日期才是通告级、只在第一行），别再只显示第一个角色的天数。拍摄中 / 自制通告本来就是一人一行按各自角色查表，不受影响。
- **游戏当前日期在文件头 @60** 的 `[年, 月, 日, 星期]`。通告档期是**三个**四元组（开放接取的周一 / 开拍的周一 / 杀青的周日），停止接取 = 开拍前一天。别把 `BigActive` 的周末日历或艺人合约日期当成当前时间。
- **公司信息 = 文件头 + `Firm` 段**：公司名在头部 @4（20 字节 Big5，遇 NUL 截断）、主角姓名 @24（16 字节）、资金 @80（int32，可以是负数 = 负债）。公司形象 / 知名度 / 公关 在 `Firm` 段：段体先是公司数量，然后每家一条 `[编号][形象字节数][每字节一个 int32][知名度][公关][0]`，**编号 1 就是我方**，2~5 是对手公司（名字在游戏的 `Firm.dat` 里，这 5 家：翱翔天際 / 綺麗之夢 / 神采藝術 / 鉅子娛樂 / 543事務所，存档只记数值与形象）。形象的字节按**有符号** int32 存（`0xAB` 写成 -85），取低 8 位再拼 Big5；解出控制字符就整段留空，不把乱码糊上界面。卡片排在「我方艺人」上面。
- **钱的写法走 `moneyText()`**：不上一万原样给（`5000`），上万拆「万」（`12000` → `1万2000`），上亿再拆「亿」（`110002000` → `1亿1000万2000`），每段都不加千分位；负数前面带 `-`（Story0001 是 `-98万1723`）。酬劳列本来就是「万」为单位，不走这个函数。
- **两张表**：`CaseFirm` 段登记的是当期还能接的通告（筹备中）；某条被接走之后编码从 `CaseFirm` 消失，但 `Case` 段里那条通告块还在，并且多出一段接取记录 —— 这就是「拍摄中」的真源。
- **筹备中的筛选**：搜索（名称 / 编号 / 类型 / 公司 / 角色）、公司下拉、类别胶囊三个独立条件取交集，外加接取情况两档 —— **未预约**（`isAcceptable()`：还没停止接取，并且有角色没被预约；「下周更新」还没开放、已停止接取的不算，读不到角色记录的也不算）与 **满足条件**（`canTakeNotice()`：在未预约的基础上，我方至少一位艺人性别对得上、九项所需数值与社交接演门槛一项不差，团体通告按队长判）。「未预约」只描述通告本身的空位，「满足条件」才是真接得上：Auto 那份 8 条未预约却一条都接不上（开局数值差 2~4 项），Story0055 后期 9 条全满足。两个标签上的数字只按存档本身算，不受搜索 / 类别 / 公司影响；选中「满足条件」不再额外挂一行说明（判定口径写在按钮 `title` 里）。
- **接取记录是一条一位艺人**：24 字节 `[状态位 0~3][艺人编号][已完成天数][?][?][酬劳]`，编号后紧跟完成天数，编号后 16 字节才是这位艺人拿到的酬劳。**进度、酬劳、角色都是按人存的**，同一条通告上四位艺人各拍各的、各拿各的钱，所以页面上是「一位艺人一行」，通告信息只在该通告第一行用 `rowSpan` 显示。
- **团体通告的进度只认队长、队员共享**：团体唱片这类通告（角色名带「團體」）是整团接下的**一份**通告，存档只给队长写了一条真实接取记录（完成天数 + 酬劳），队员名下那条 `done=0 / pay=0` 是参与清单带出来的噪声，不是他自己的进度。若照单全收会把 Auto 的 CD602 銀河（千金小姐：队长萧依莉 10/25、4150 万，队员苏嫚君）显示成队员 0/25、0 酬劳。所以构造 `shooting.casts` 后，按 `teams` 找到通告里成员所属的团体，用队长（`memberIds[0]`）那条进度覆盖全部队员的 `doneDays / pay / workDays / daysPerWeek / needDays / canShootDays / risk / status`；两行显示同一组数字。仍是一位艺人一行，只是数字共享。
- **伪记录靠筛**：块尾的日期段里年份/日号会撞上 1、2、6 这类小艺人编号。判定条件是状态位 0~3、完成天数 ≤ 60、中间两字段 ≤ 99、酬劳要么 0 要么 ≥ 1000，同一艺人只取第一条。
- **角色按性别落格**：存档只记「艺人 ↔ 通告」，没有「艺人 ↔ 角色」。按接取顺序把每位艺人放到第一个性别对得上、还没被占的角色上（男→男主角/男配角，女→女主角/女配角）；只有一个角色的通告全员共用该格。
- **预约要按角色号精确落格**：存档里另有一组 52 字节记录 `[6][5×int32 ASCII 通告码][int32 角色号][int32 艺人编号][5×int32 全 0]`，落不到 192 字节的角色记录上。只按性别猜会把 Story0011 小熊寶寶苏嫚君的女配角误占成女主角。**尾部 5 个 int32 必须全 0**才算真预约：Story0014 的 CF095 意美 好吃篇里有一段 `[6][CF095][1][16][0,1,0,0,0]`，扫描时很像真记录，但萧依莉根本没接取；不校验尾部就会凭空显示「已预约」。真记录（Story0007 CF014、Story0011 TV0482 等）尾部都是 0。
- **社交接演门槛从存档读**：角色记录的 `off+76 叛逆 / +80 性感 / +84 亲和`（int32，与艺人 social 前三项同量纲、直接比、不 ×10，三项全 0 即无门槛）是隐藏接演条件，进「所需数值」列（品牌色 chip、无等级）并纳入数值对比与满足条件筛选。通告库 `notices.json` 的 `special{rebellion,sexy,affinity}` 有同类数据但不全（主持 / 唱片类无记录），所以以存档为真源；槽位经 27 份存档 × 231 角色对照确认。
- **艺人友好度 / 送礼数**：存档头部 284 字节定长的友好度表，每条 `[友好度][送礼数][256/257][艺人编号]`，按编号反查附到艺人卡片；两格都是整数、不缩放。Story0002 萧依莉 #6 友好度 141；送礼数不读艺人状态块 social 后的 0/1 标志位，真值是 Auto #6 = 2、Ending0001 #65 = 10 / #74 = 5 / #76 = 2 / #12 = 4。友好度是活档字段，游戏推进会改写，测试真值以注入的固定快照为准。
- **制作人好感（场景下方「制作人好感」区块）**：清单数据 `src/lib/caseProducers.ts`，按唱片 / 电视剧 / 电影 / 广告 / 主持 / 其他六列，每位给 `code`（存档角色编号）+ 名字，擅长 / 讨厌 / 出现条件等后续逐类补。友好度真源是**独立于艺人表的另一段 284 字节定长角色友好度表**：`+0` 角色编号、`+148` 友好度整数，涵盖制作人段（4xx 唱片 / 5xx 电视剧 / 6xx 电影 / 7xx 广告）与前段 NPC / 其他角色（3 賀總 / 38 史蒂芬 / 39 丹尼斯…）。制作人段 `+4` 类别=编号百位，以 code=401（kind=4）为锚点按 284 步长连读，中间空槽（如 411 kind=0）跳过不中断；NPC / 其他段 `+4` 类别不是百位，改用「code=3 且 +284 处 code=4」双连续锚点定位表头（40+ 份存档 base 712/772 都能命中），再顺扫到 code=1399（表尾 1400+ 是场景物件、友好度恒 0），覆盖 3 賀總 / 38 史蒂芬 / 39 丹尼斯 / 101 王瑞恩 / 1301 加賀大澤 / 1302 史麥克等；空槽跳过、先到优先。`parseProducerFriendship()` 两段都读进 `result.producerFriendship`，UI 按 `producer.code` 反查显示（无值显示横杠）。Ending0001 真值：唱片 401 周映彤 711 / 501 小熊 999 / 1301 加賀大澤 686；电视剧 301 陳革非 506 / 201 鄭超一 723；电影 101 王瑞恩 999 / 1302 史麥克 542；广告 601 陈查理 999 / 701 麦克 544；主持 302 強尼戴 345 / 202 錢鈞 427；其他列 3 賀總 95 / 38 史蒂芬 100 / 39 丹尼斯 70（用户先报 79，存档核实为 70，已更正）。
- **一般物品「好感度」列**：在道具面板「一般物品」页签按当前存档签约艺人反查 `gifts[giftSlots[艺人编号]]`，只列加成 > 0 的艺人，按数值降序（同值按姓名）排成「萧依莉+4」这样的小胶囊；三档统一用品牌色系靠深浅区分——＋4 实心 `bg-brand` 白字、＋3 `bg-brand-soft` 深字、＋1/＋2 淡 `bg-surface-soft` + 品牌色字，无数据的写横杠。表头 `title` 写明来源是游戏 `Item.dat`。其他两个页签不显示这一列，占位行按页签补空 `<td>` 防列数错位。
- **道具表列宽**：`table-auto` + `min-w-max`，编号 / 类型 / 数量 / 好感度定宽（好感度 `w-68` 容得下四个胶囊），**名称与说明自适应**按内容撑开——名称格里是「道具名 + 属性加成」两段，Ending0001 的「漸層反光太陽眼鏡 口才+40 演技+25 自信+5」要 300px+，定宽会把它挤成两行；说明去掉 `truncate` 显示全文。总宽超过主栏时由外层 `overflow-x-auto` 横向滚动，不靠压缩列宽换行。类型胶囊加 `whitespace-nowrap` 防「一般物品」被折成两行。

- **拍摄中的判定**：块里有接取记录、编码已经不在 `CaseFirm`、自家艺人里还有人没拍够 `Length` 天数、且今天不晚于杀青日。艺人的作品清单是**历史累积**（十几年旧作都留着），只按它反查会把早已杀青的旧块捞出来，必须叠加日期这一道。
- **不做「已完成」页签**（玩家口径：拍完的通告已经没意义）。自家艺人都拍够天数、或今天已经过了杀青日的，整条不进表；行内状态只留 `pending` 待开拍 / `shooting` 拍摄中 / `done` 已完成三档。开拍与杀青在表格里**必须带年份**（游戏跨三个年头，只写 `12/15` 分不清哪一年）。
- **提示只有两档**（`riskOf()`，阈值 `RISK_SLACK_DAYS = 5`）：还差天数 = `Length` 表工作天数 − 存档完成天数，剩余额度 = 剩下的日历日按每週上限折算（`shootableDays()`）。`额度 − 还差 ≤ 5` 判「逾期风险」（余量太薄，艺人会失误），`额度 < 还差` 判「违约提醒」，其余不出提示。不写「排得下 / 刚好够」这类结论。执行期间下面的「工作 N 天 / 每周 ≤N 次」必须拆成两个各自带背景的 `inline-flex` 胶囊、外层不铺背景：两枚胶囊换行时留下的只是正常行距，不会再出现一整块空白背景。

- **自制通告有自己一套档期**：块里按顺序躺着几个 `[年][月][日][周几]` 四元组，第一个**永远是周一**（全库 446 个块无一例外）= 开拍日，第二个 = 杀青日，再往后（有的块有）是上档 / 下档。所以状态照样能推：今天在开拍日之前是 `pending`、夹在中间是 `shooting`、过了杀青是 `done`（`readSelfMadeDates()`）。开拍不是周一的块一律当「无档期」，宁可留空也不猜。**没人接的通告一律 `pending`（未开拍）**，哪怕今天正落在档期里 —— 档期只是挂在列表上的排期，没人进组谈不上拍摄中；档期已经过去而始终没人接的，状态仍是「未开拍」，档期列下面只写「还没人接」—— 档期过没过已经在上面的开拍 / 杀青两行写清楚了，不再重复判断（也避免出现「还没开拍却说档期已过」这种自相矛盾的小字）。

## Electron 桌面端（存档解析）

桌面端是独立入口 `desktop.html`，只挂**存档解析**一个页面，其它五个页签入口都不渲染；和 Web 端共用同一份 `CaseReaderApp` 与样式令牌。以后要把别的页面放进桌面端，只需在这个入口加 tab，组件都是现成的。

- **三层结构**：`desktop.html`（Vite 第三个输入）→ `src/desktop/main.tsx`（挂 `DesktopApp`）→ `src/desktop/DesktopApp.tsx`（顶栏 + `<CaseReaderApp externalSave>`）。`CaseReaderApp` 新增可选 prop `externalSave: {buffer, name, token}`，`token` 递增就重新解析；Web 端不传这个 prop，仍走拖入 / 选文件。桌面端自己加载 `data/guide.json` 并挂 `GuideDataContext`，场景卡 hover 的提示与主站共用同一份文案。
- **自定义协议 `mxzy://local/...`**：`electron/main.cjs` 在 `whenReady` 前 `registerSchemesAsPrivileged` 声明为标准协议，`protocol.handle` 把请求映射到 `dist/` 并补 MIME。这样页面里所有 `fetch('data/*.json')`（含 `case-tables.json?`）都能在打包后正常加载——`file://` 下本地 fetch 会被 CORS 拦。开发时可设 `MXZY_DESKTOP_DEV_URL` 走 Vite dev server，跳过协议。
- **只读文件桥**：`electron/preload.cjs` 经 `contextBridge` 暴露最小接口（`getState` / `chooseDir` / `refresh` / `setAutoFollow` / `setSelected` / `readSave` / `onState`，File 菜单另加 `openSave` / `requestReload` / `onOpenSave` / `onReloadRequest`），没有任何写文件或系统能力。目录由用户**自己选**（`dialog.showOpenDialog` 的 `openDirectory`，不写死、不猜游戏安装路径），只把上次选的目录 / 自动跟随开关 / 选中档位记在 `app.getPath('userData')/desktop-config.json`。
- **稳定读取**：Auto.sa2 游戏运行时会被覆盖，`readSaveStable()` 读前后各 stat 一次，大小或修改时间变了就等 90ms 重读，最多 4 次，避免半截文件进解析器。`readSave` 经 IPC 把 Buffer 转成 `Uint8Array` 克隆给渲染进程，再转回 `ArrayBuffer` 交给 `parseSave`。
- **原生 File 菜单**：主进程 `registerMenu()` 建 File（打开存档… `CmdOrCtrl+O` / 重新载入当前存档 `CmdOrCtrl+R` / 退出）+ Edit / View / Window / Help 标准角色。`打开存档…` 用 `dialog.showOpenDialog` 的 `openFile`（默认路径取上次选的存档目录、只筛 `.sa2`），`readSaveStable()` 读完后由 `desktop:openSaveResult` 推给渲染进程的 `feedSave`——和目录里点档位共用同一条解析通道，不另写解析逻辑。**重新载入认最后打开来源**：`openFileRef` 记着菜单打开的文件（path+name）就重读它，否则读目录里的当前档位；换档位 / 选目录 / 开自动跟随都会清掉这个引用，避免两个来源打架。`desktop:openSave` / `desktop:requestReload` 两个 IPC 专供回归脚本跳过系统对话框触发同一条链路。
- **自动跟随**：主进程 `fs.watch(saveDir)` 变化时节流 350ms 推 `desktop:state`（含最新清单），渲染进程比对当前档位的 `path|mtime|size` 指纹，变了才重读；主动读取也会记下指纹，避免“读到新快照→再触发读取”的死循环。没开自动跟随时，点「读取当前游戏状态」或换档位才读。
- **启动注意**：本环境预设了 `ELECTRON_RUN_AS_NODE=1`，会让 electron.exe 以纯 Node 模式跑主进程（`require('electron')` 只剩路径、协议 API 全丢）。启动必须清掉：`env -u ELECTRON_RUN_AS_NODE electron .`；npm 的 `desktop` 脚本在用户机器上通常没这个变量，不受影响。Electron 二进制首装若从 GitHub 下载失败，用 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ node node_modules/electron/install.js`。
- **回归**：`scripts/cdp_desktop.mjs`（18 项，连调试端口验证独立入口无其它页签、自定义协议加载内置表、文件桥注入、真实 IPC 读档后渲染游戏时间与通告表格，以及 File 菜单打开存档桥、打开后顶栏显示来源与文件名、走同一解析通道渲染、`requestReload` 重读的是菜单打开的文件而非目录档位）。启动：`env -u ELECTRON_RUN_AS_NODE MXZY_DESKTOP_DEBUG=9223 electron .`，再 `MXZY_DESKTOP_DEBUG=9223 node scripts/cdp_desktop.mjs`。本环境 GUI 窗口十几秒会被回收，CDP 要和启动写在同一条命令里跑完。
- **打包**：`electron-builder --win` 配 `signAndEditExecutable: false`（个人项目无签名证书，跳过 rcedit/签名；本环境 winCodeSign 解压还会因 macOS 符号链接权限失败，这个开关一并绕开）。产物在 `release/`。本环境 NSIS 安装包的 makensis 阶段另有权限问题，实际发行用免安装 zip：把 `release/win-unpacked/` 里的内容压成 zip（顶层就是 exe 与 `resources/app.asar`，用户解压即用），已对打包后的 exe 跑过 `cdp_desktop.mjs` 回归验证。`build/icon.ico` 由 `public/favicon.ico` 放大生成（256px），是网页版顶栏同一张「明3 3in1」logo。
  - **应用图标注入**：`signAndEditExecutable: false` 会连 rcedit 一起跳过，exe 里保留的是 Electron 默认原子图标（任务栏/文件夹里看到的不是我们的 logo）。`package:desktop` 脚本在 `electron-builder` 之后接 `node scripts/inject_desktop_icon.mjs`，用 electron-builder 缓存里的 `rcedit-x64.exe` 把 `build/icon.ico` 注入 `release/win-unpacked/*.exe`。改了 logo 后重新打包会自动注入；若只重压 zip，记得先跑一次这个脚本再压。

## 体量统计口径

页面上显示的是**字数**，不再是段落数：「约 X 字」取正文非空白字符数（含标点），`table` 块的单元格也算在内，分类页按「自身 + 全部子条目」累计；叶子条目只显示字数，没有子条目时不再显示「0 个子条目」。超过 1 万字折算成「1.2 万」，由 `src/lib/guide.ts` 的 `countChars` / `countCharsDeep` / `formatCount` 统一处理。

## 内容块渲染

`ContentBlockList` 把内容块按 `group` 聚合，一个 group 就是一段不可拆的整体：

- group 首块是 `event`（编号事件）时，整组渲染成**一张卡片**：编号徽章 + 正文在第一行，其下的选项、补充说明、`提醒：` 提示条都与正文左对齐缩进在卡内，不会出现「选项落在卡片外面」的割裂感。事件行原本写在编号后的 `（自动）`、`（场景）`、`（跟随）`、`（手动）` 会被解析成 `tag` 字段，渲染成彩色标签（墨灰 / 莓红 / 金 / 紫），一眼能看出触发方式。四色各自偏一个色相、刻意避开主色玫瑰，`自动` 与 `场景` 才不会糊成一片；对应令牌是 `--color-auto*` / `--color-scene*` / `--color-gold*` / `--color-violet*`。
- 选项（`A.先接电话——…`、`C 关古威…`、`b.自制唱片5张…`）统一由 `OptionLine` 渲染：`A`/`B`/`C` 提成白底小方块徽章（统一大写），整行再往右缩进一级、铺一层中性灰底（`--color-choice*`），与事件正文区分开；没有字母的补充行（`旗下艺人为…`）只留一条灰色竖线。docx 里字母后有点号也有空格，解析器（`OPTION_RE`）两种都认，前端正则同样放宽，因此同一份清单不会一半带徽章一半是纯文本。
- group 首块是带 `id` 的 `heading` 且有选项时，渲染成 `QuestionCard`（开局问题用的选项卡，带跳转 chip）。
- `table` 块交给 `DataTable`：表头用 sidebar 底色，数值列右对齐并用 `tabular-nums` 对齐位数，奇偶行交替换色；`highlight` 列为真的列会把该列最高值套上 `bg-brand-soft` 胶囊，列上有 `growthKey` 时该格会多渲染一行「＋成长值」（最高值转金色）。最高值只在该列唯一时才标，和游戏内表格「多於一人時不會標示」一致。
- 其余情况逐块渲染：`section`（`#`/`*` 大标题）、`heading`、段落、提示条各自成段。

## 攻略 ⇄ CG 映射

两张手写表是唯一事实来源，改映射只改这两张，再重跑对应脚本：

| 表 | 用途 | 格式 |
| --- | --- | --- |
| `sources/cg-links.tsv` | 一对一：事件 → 它出的那张（或那几张）CG | `节点id <TAB> 事件号 <TAB> cgId[,cgId] <TAB> 章节?` |
| `sources/cg-node-links.tsv` | 多对一：多张 CG 共用一个事件，或只能整页落点 | `cgId <TAB> 节点id <TAB> 备注 <TAB> 事件号? <TAB> 章节?` |

- **章节列必须写「最内层」heading**，`☆d2` 子标题（「拒绝」「在巴黎」「同志传闻」）也算一层。同一编号在一页里出现两次时不写章节会报 `ambiguous event`，写错报 `no such event … @ 章节`，整条映射让生成直接失败，不会静默断链。
- `extract_guide.py` 的 `apply_cg_links()` 给命中事件的块补 `cgIds` 与 `anchor="ev<块下标>"`；事件卡的 DOM id 用 `head.anchor ?? ev<index>` 兜底，所以任何事件都能被 `#/guide/<nodeId>~ev<n>` 深链，哪怕它没有 CG。
- `extract_cg.py` 的 `apply_node_links()` 处理多对一：有事件号就现算 `ev<块下标>`（美丽之星写真集 18 张都锚 #14），没有就只写整页落点。两份结果分别落在 `guide.json` 的块上和 `cg.json` 的 `item.guide`。
- 前端 `CgApp.linkFor()` 先认事件级（`cgIds` 反查），再认页面级；多个候选落点时**优先 `other-events/luousang/` 前缀**——三人恋情事件在各自艺人页只做浏览，跳转与收集统一走剧情整理。`src/lib/cgOrigin.ts` 另外记住「从哪条事件点进图鉴的」（sessionStorage，不进存档），同一张图有多处出处时按原路返回。
- 允许的重复：同一张 CG 出现在同节点的两个事件（苏嫚君 CG05 圣诞布置，育幼院 #40 与达成结局 #55 各一次），以及 `other-events/luousang/` 五个分支页之间（同一段剧情写了五遍）。跨节点重复会被 `test_cg_links.py` 拦下，除非登记进 `DUPLICATED_ACROSS_NODES`。
- 事件池里被挡掉的重复章节由 `src/lib/tracker.ts` 的 `POOL_SKIP` 按「节点 id + 章节名」配置（路风 / 桑禾蓓的整个「事件」节、欧怡青的「路欧恋」章）；**被挡的线仍递增序号**，其余线的 id 不位移，老存档才不会失联。

## 锚点跳转

攻略正文里带 `id` 的标题块可以在页内跳转，`target` 指向目标块的 `id`：

- 「游戏初始问题」每题是一个 `heading` 块（`id: q1`…`q14`），每个选项记录 `target`（下一题）、`targetLabel`（显示为「接问题３」或终止的「问题结束」）、可选的 `reward` 与 `hint`。
- 点击跳转链接会平滑滚动到目标、加一圈高亮闪动，并把地址写成 `#/game-guide/initial-questions~q3`（用 `replaceState`，不会触发 `hashchange` 重置选中项）。
- 刷新或分享该地址会直接落回对应题目：`useHashSelection` 只取 `~` 之前的部分作为节点 id，`useAnchorJump` 负责滚到锚点。
- 「本页小节」在宽屏常驻正文右侧一列（`PageRail`），窄屏仍保留正文顶部的折叠卡片；两者都是**布局里的一列 / 一张卡，不是浮层**，因此永远不会盖住正文。右侧栏列出本页全部 `section` / `heading`，点击与「接问题Ｎ」一样平滑滚动 + 高亮闪动，当前读到的小节用玫瑰底色高亮（`useActiveOutline` 用 `IntersectionObserver` 取窗口上半区最靠前的小节）。`section` 编号为 `1.`，`heading` 子标题按父级编号成 `2.1.` 并向右缩进一格、左侧带一条细竖线，层级一眼可分（`outlineOf` 里的 `depth` 字段来自数据）；编号规则由 `numberOutline` 统一生成，侧栏与顶部卡片共用。

## 本页导航与回到顶部

- 右侧栏顶部可以折叠：点右上角箭头收成一条 36px 的竖排「本页小节」标签，点标签再展开。折叠状态存在 `localStorage`（`guide.rail.v1`），刷新后保持；**折叠时列宽不变**，正文不会左右跳动。

- 窄屏没有侧栏时，右下角在读过 320px 后浮出圆形 `^` 按钮；正文右侧为此预留了 24px 空档，按钮落在空隙里，不压在文字或卡片上。

## 目录排序

侧栏目录可以按自己的习惯重排，但**只在同一层级内**移动：把「初始事件」拖到「游戏初始问题」上方，它就成了该类目的第一条；把「艺人事件簿」拖到「经纪人事件簿」上方，整个艺人事件簿连同它下面所有条目一起上移。类目里的条目不能被拖进另一个类目，跨层级一律不接收（悬停时不会出现插入线）。

- 拖拽落点是目标行的上半 / 下半，分别表示「插入到它之前 / 之后」，落点处显示一条玫瑰色插入线，被拖的行变淡。
- 顺序存在 `localStorage`（`guide.tree-order.v1`），只记录**真正动过的层级**（父级 id → 子 id 列表）。重新生成 `guide.json` 时，未动过的层级不受影响；列表里已不存在的 id 会被忽略，新增条目回落到该层级末尾。
- 只改顺序不改数据：页头的五个分类 tab、搜索命中的排列、「上一条 / 下一条」都按新顺序走。URL 里仍是稳定的节点 id，重排不会让链接失效。
- 侧栏标题右侧出现「恢复默认」时表示顺序已被改过，点一下即回到脚本生成的顺序（同时清掉本地记录）。
- 键盘可用 `Alt+↑` / `Alt+↓` 把焦点所在的条目上移 / 下移一位。触摸屏不支持 HTML5 拖拽，此时每行右侧显示 `↑` `↓` 两个按钮（`touch:` 变体，`pointer: coarse`）。

## 样式约定

- 颜色、字号、圆角、阴影只在 `src/styles/global.css` 的 `@theme` 中定义，组件统一使用 `text-ink`、`bg-brand-soft`、`rounded-ui-md` 这类语义类，不写裸色值。

## 图片加载与占位

- 起因：GitHub Pages 从国内访问，一张 100KB 的图常要几秒（实测一张 128KB 头像 5.3s）。原图按最大尺寸入库（CG 1100px、角色头像 400×300 PNG、封面 1110px JPG），而卡片只显示 380px、侧栏头像只有 20px，等于每次都在下几倍用不上的像素。
- `scripts/build_image_thumbs.py`（需 Pillow）把 `public/images/` 下每张原图生成统一 webp 缩略图，镜像到 `public/images/thumbs/`；**原图保留给灯箱看大图**。规则只有一条：`images/<dir>/<name>.<ext>` → `images/thumbs/<dir>/<name>.webp`。宽度上限 `*-logo` 128px、`*-cover` 800px、其余 560px，不放大，quality 74 / method 6。产物随仓库提交，构建时随 `public/` 进 `dist/`。当前 346 张：18.6MB → 7.4MB（2.5×），其中头像平均 2.8KB。
- `src/ui/SmartImage.tsx` 是全站唯一的 `<img>` 出口（灯箱叠原图那一层除外）：按上述规则换缩略图、`loading="lazy"` + `decoding="async"`、缩略图失败静默退回原图、首屏 `priority` 用 eager + `fetchPriority=high`。`skeleton` 开启时，加载期间是淡色扫光 + 图片图标的占位层，到图后淡入；骨架只在 `IntersectionObserver`（`rootMargin: 600px`）判定接近视口时才渲染，避免一页几十个动画在后台空跑。`prefers-reduced-motion` 下动画停掉。
- CG 灯箱先显示卡片已缓存的缩略图，后台用 `new Image()` 预载原图，完成再叠一层淡入（`data-cg-lightbox-full`），点开大图不用盯着黑屏等。**两层图都铺满舞台并用 `object-fit: contain`，算出的内容矩形完全一致**：原图到位时只是由糊变清晰，不会从 560px 的小图突然放大成 1041px（淡入 0.4s 且带 `both`，避免首帧闪一下原图）。图片元素铺满舞台后，`event.target` 不再能区分图片与四周留白，点黑底关闭改为按缩略图宽高比算出的内容矩形判定：点在图上不关、点在留白才关。
- `scripts/test_image_thumbs.py`（4 项，零第三方依赖）锁「每张原图都有缩略图 / 是真 webp 且更小 / 无孤儿 / 总体积减半」；`scripts/cdp_image_loading.mjs`（17 项）用 CDP `Fetch` 暂停图片请求复现慢链路，验骨架出现与收起、缩略图路径、首屏下载体积、缩略图失败回退；灯箱部分锁住「预览图一上来就铺满舞台」「原图与预览图显示矩形一致」「点图不关、点黑底才关」，并确认明星志愿3 的灯箱也是尺寸不变、只由糊变清晰。此外覆盖明星志愿3 的 CG 图鉴与攻略封面（两个站点共用同一套组件，回归不能只测一个入口）。

| `python scripts/build_image_thumbs.py` | 全量重建 `public/images/thumbs/` 的小图（需 Pillow）；`--check` 只校验不写 |

**测试范围**：只改甜蜜乐章的内容或组件时，跑 `npm run test:sweet` + `node scripts/cdp_sweet_entry.mjs` 就够了，不必跑全量 `test:guide` 和其它站点的 `cdp_*.mjs`。只有动到共享层（`global.css` 令牌、`patterns.ts`、`src/ui/*`、路由、`useGuideData`、`treeOrder`）时，才需要补跑原站回归。改图片管线或 `SmartImage` 额外跑 `python scripts/build_image_thumbs.py --check` + `node scripts/cdp_image_loading.mjs`。

**解析回归**：解析脚本里积累了大量角色专属分支，改一个共享正则可能悄悄改坏别的角色页，所以 `test_extract.py` 会重跑真实管线，并断言产物与已提交的 `guide.json` **逐字节一致**。改完解析规则先重生成再测：

```bash
python scripts/extract_guide.py
npm run test:guide
```

**通告数据回归**：`test_notices.py` 只依赖标准库，检查编号唯一、每条都有角色、等级/星级表完整，装了 openpyxl 时还会把推导出来的区间与原始 xlsx 逐格比对（1100+ 组合）：
